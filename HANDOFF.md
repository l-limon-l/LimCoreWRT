# LimCoreWRT — состояние работ

Документ для продолжения в новом чате. Актуален на **11 августа 2026**.

---

## 1. Доступ к роутеру

```bash
ssh root@192.168.1.1
```

Вход по SSH-ключу, пароль вводить не нужно (пароль есть в переписке первого чата, сюда намеренно не вынесен — файл лежит в репозитории).

Полезное на устройстве:

| Что | Где |
|---|---|
| Настройки | `uci show limcore` |
| Сгенерированный конфиг ядра | `/var/run/limcore/core.json` |
| Лог ядра | `/var/run/limcore/core.log` (+ `.log.1`) |
| Лог наблюдения за связью | `/var/run/limcore/health.log` |
| Управление службой | `/etc/init.d/limcore {start,stop,restart,status}` |
| Скрипты | `/etc/limcore/scripts/`, `/usr/share/limcore/scripts/` |
| Бэкенд интерфейса | `/usr/share/rpcd/ucode/luci.limcore` |

Железо: OpenWrt 25.12.5, aarch64_cortex-a53, apk-tools 3.0.5, overlay ubifs 95.6 МБ (занято 41%).

**Важное ограничение по проверкам.** На компьютере включён VPN, поэтому все проверки ведутся с роутера. Проверки через ПК — крайний вариант и только когда вы на месте и можете обеспечить условия.

## 3. Что было сделано

### Переименование и чистка
- Всё переименовано в **LimCore**, включая пути (`homeproxy` убран отовсюду).
- **hiddify-core удалён полностью** — и пакет, и все ветки разбора его формата в генераторе конфига. Остался только sing-box-extended (форк shtorm-7).
- Удалены репозитории passwall, дававшие предупреждения `UNTRUSTED signature`.

### Починка установки ядра
Симптом был: установщик писал «singbox установлен», а интерфейс показывал «✗ не найдено».

Причина — обрыв загрузки: пакет регистрировался в apk, а бинарник до диска не доезжал. Исправлено в `core_mgmt.uc`: проверка размера скачанного файла, проверка наличия `/usr/bin/sing-box` после установки, откат при неудаче, показ настоящей ошибки apk вместо молчания.

### Починка самообновления
Кнопка «Обновить LimCore» не работала по двум независимым причинам:
1. rpcd убивал дочерний процесс — вылечено запуском через `setsid`;
2. `/usr/bin/limcore-update` приезжал с правами `100644`, то есть не исполнялся — выставлен бит запуска и вызов через `sh`.

Заодно: проверка «жив ли процесс» переведена с `pgrep -f` (он находил сам себя и всегда возвращал «работает») на PID-файл.

### Подписывание пакетов
Настроено сквозное подписывание APK: ключ в секретах GitHub, `apk mkpkg --sign-key` в сборке. Предупреждений о неподписанных пакетах больше нет.

> Уточнение к более раннему объяснению: apk сопоставляет ключи **по содержимому, а не по имени файла**. Переименование ключа было безобидным, но обоснование, которое я тогда привёл, было неверным.

### Discord
Голос и демонстрация экрана заработали после добавления диапазонов **19294–19344** и **50000–50100** — в правило маршрутизации и в список перехвата одновременно. До этого в звонке был пинг 5000.

### Cloudflare WARP
Добавлен как родной эндпоинт `warp` в sing-box с `detour` на основной прокси — то есть WARP работает поверх VPN, а не вместо него.

Два режима: `all` (весь проксируемый трафик) и `domains` (только перечисленные суффиксы). Есть вкладка «Warp» с переключателем и кнопкой проверки.

**Грабли, стоившие двух обрывов связи при живой проверке:** `api.cloudflareclient.com` входит в списки Re:filter, поэтому регистрация WARP маршрутизировалась в сам WARP — замкнутый круг. Лечится правилом `cloudflareclient.com → main-out`, стоящим **перед** всеми правилами WARP. Это правило трогать нельзя.

### Проверка обновлений
- Кнопка «Проверить обновление» с показом «установлено / доступно».
- Проверка расширена на **все** компоненты: sing-box, ByeDPI, Zapret.
- Результат кэшируется на 15 минут в `/tmp/limcore-update-check.json`, на каждый запрос к GitHub одна повторная попытка (сам `api.github.com` идёт через прокси и иногда отвечает ошибкой или упирается в лимит запросов).
- Добавлена возможность автоматической проверки по расписанию через cron с метками `#limcore_*`.

### Прочее
- Конфиг проверяется через `sing-box check` **до** запуска — битый конфиг больше не роняет службу.
- Логи ротируются, а не обрезаются, и живут достаточно долго, чтобы их можно было прочитать.
- Исправлено размножение ip-правила tproxy при каждом перезапуске.
- Установщик берёт `/releases/latest` вместо первого попавшегося релиза (раньше мог поставить версию старее установленной).

## 4. WARP: текущая настройка

Режим `domains`. Через WARP идут только:

```
gemini.google.com
aistudio.google.com
generativelanguage.googleapis.com
cloudaicompanion.googleapis.com
cloudcode-pa.googleapis.com
daily-cloudcode-pa.googleapis.com   ← настоящий бэкенд Antigravity
antigravity-unleash.goog            ← переключение возможностей Antigravity
oauth2.googleapis.com               ← обновление токена, см. ниже
ogs.google.com                      ← сетка приложений Google, см. ниже
```

Проверено на живом трафике с компьютера: соединения к `daily-cloudcode-pa.googleapis.com` уходят в `endpoint/warp[warp-out]`, посторонний трафик — в `outbound/vless[main-out]`. Разделение работает.

### `cloudaicompanion` — ложный след, стоивший двух чатов

Antigravity возвращал `400 "User location is not supported for the API use."` с заголовком `X-Cloudaicompanion-Trace-Id`, и домен `cloudaicompanion.googleapis.com` был добавлен по этому заголовку. **В трафике этого домена нет вообще.** Это внутреннее имя службы Google, оно попадает только в заголовок трассировки. Реальный хост — `daily-cloudcode-pa.googleapis.com`, он виден в `/connections` Clash API.

Под старый суффикс `cloudcode-pa.googleapis.com` он не подходил: sing-box сравнивает домены **по меткам, а не по строке**, поэтому `daily-cloudcode-pa` — другая метка. Правило молча не срабатывало.

### Регион определяется по личности, а не по адресу запроса

Исправление маршрута ошибку **не убрало**. Разбор:

| Путь | IP | Cloudflare | Gemini API без ключа |
|---|---|---|---|
| Основной узел | `157.180.98.4` | `loc=FI` | `API_KEY_INVALID` |
| Через WARP | `104.28.222.16` | `loc=FI` | `API_KEY_INVALID` |

У Gemini API проверка региона стоит **до** проверки ключа, значит регион принят с обоих адресов. Запрос без токена к `daily-cloudcode-pa.googleapis.com` с обоих путей даёт `401 UNAUTHENTICATED`, а не `400` про регион — то есть вердикт о местоположении выносится **после** аутентификации, по токену.

Вылечилось повторным входом в аккаунт Google из Antigravity, пока весь путь входа шёл через WARP. Старый токен был выпущен на российский адрес, и API отказывал независимо от того, как маршрутизирован сам запрос.

`oauth2.googleapis.com` оставлен в списке именно поэтому: обновление токена должно уходить с того же выхода, что и API. `accounts.google.com` добавлялся на время входа и **убран** — через него идёт не только вход, но и обновление куки всех сервисов Google, и WARP на нём тормозит слишком многое. Если вход перестанет проходить, добавить снова на время входа.

### Сетка приложений Google — противоположный случай

Из сетки за кнопкой 3×3 пропала плитка Gemini. Отдаёт её `ogs.google.com` («One Google»), а не страница поиска. Достаточно было добавить один этот домен в WARP — плитка вернулась.

Здесь регион решается **по адресу запроса**, а не по аккаунту. Проверено по записи соединений: `ogs.google.com` ушёл в `warp-out`, `www.google.com` при этом остался на `main-out`. То есть один и тот же на вид отказ по региону у Google приходит из двух разных механизмов, и лечится по-разному — не переносить вывод из одного случая в другой.

`www.google.com` в списке намеренно нет: через него идёт весь поиск, а WARP режет скорость после сотни мегабайт.

Почему не режим `all`: WARP примерно вдвое режет скорость даже до троттлинга, а после него — в двадцать раз.

## 7. Грабли, на которые не стоит наступать снова

- **`[ -n ${IPKG_INSTROOT} ]`** без кавычек всегда истинно — из-за этого тело postinst не выполнялось. Кавычки обязательны.
- **`access('/proc/' + '')` возвращает истину** — при проверке PID нужна защита от пустой строки.
- **`regexp()` в ucode с `\S`** молча не находит ничего. Использовать разбиение по пробелам.
- **ubifs сообщает о свободном месте пессимистично** сразу после записи (22 МБ против реальных 54 МБ). Не пугаться и не менять пороги по горячим следам.
- **Сжатие overlay — 2.21x**, считается как `du` против `df`, а не `du` против `du`. Пороги в `core_mgmt.uc` (`FULL_OVERLAY_RAW_KB=81920`, `FULL_OVERLAY_COMP_KB=32768`) верны, я их однажды сломал неверным замером и вернул обратно.
- **Одиночные кавычки внутри `echo -e '...'` в CI** закрывают строку — так однажды на раннере выполнился `/etc/init.d/rpcd restart`. Двойные кавычки.
- **Инструмент Bash коверкает обратные слэши в heredoc.** Для скриптов со спецсимволами писать отдельный файл, а не heredoc.
- **Модули с `export` не проходят `ucode -c -o /dev/null`** — это нормально, не считать ошибкой.
- **`mv` не отбирает файл у того, кто его пишет.** Ротация логов через `mv` положила роутер целиком (см. раздел 9). Процесс пишет по inode: после `mv` он продолжает писать в повёрнутый файл, а новый остаётся пустым навсегда. Только `cp` + обрезание на месте.
- **`/var/run` — это tmpfs, то есть оперативная память.** Всё, что там растёт без предела, съедает RAM, а не флеш. На 240 МБ это смертельно.
- **Имя службы в заголовке ошибки — не имя хоста.** `X-Cloudaicompanion-Trace-Id` увёл в сторону на два чата. Смотреть, куда клиент ходит на самом деле: `curl -s http://127.0.0.1:9090/connections` на роутере отдаёт `host`, `destinationIP` и `chains` по каждому живому соединению. Это единственный надёжный способ узнать домен и то, каким выходом он ушёл.
- **`domain_suffix` в sing-box сравнивает метки, а не строку.** `cloudcode-pa.googleapis.com` не покрывает `daily-cloudcode-pa.googleapis.com`.
- **На роутере нет `paste` и `pgrep`.** Скрипты разбора писать на `awk`, процессы искать через `ps w | grep`.
- **`scp` на роутер не работает** — нет `sftp-server`. Заливать файлы через `ssh root@… 'cat > /tmp/файл' < локальный`.

## 9. Разбор отказа 12 августа 2026

Утром роутер перестал отвечать целиком: не открывалась даже админка по `192.168.1.1`, помогла только перезагрузка.

**Причина — наша регрессия в ротации логов** (коммит e689cfd, где обрезание заменили на `mv`).

`clean_log.sh` делал `mv core.log core.log.1` и создавал новый пустой `core.log`. Но sing-box держит лог открытым и пишет по inode: после `mv` он продолжал писать в `core.log.1`, а `core.log` навсегда оставался нулевым. Скрипт же измерял только `core.log` — то есть ротация не срабатывала больше никогда, и `core.log.1` рос без предела.

Подтверждение прямым наблюдением, а не рассуждением:

```
/proc/<pid sing-box>/fd/3 -> /tmp/run/limcore/core.log.1
core.log    0 байт (не менялся с момента ротации)
core.log.1  608853 → 613701 байт за 20 секунд
```

`/var/run` — это tmpfs, 117 МБ при 239 МБ памяти. Лог съел память, и роутеру стало нечем работать. Отсюда и симптом «недоступна админка»: это была не сеть, а нехватка RAM. По времени сходится: служба стартовала 11 августа около 15:03, отказ — около 09:00, то есть примерно 18 часов роста.

**Исправление:** `cp` + обрезание на месте — inode сохраняется, писатель остаётся направлен на файл, который мы можем очистить. Плюс предохранитель: если `*.log.1` перевалил за десятикратный порог, он обрезается на месте — это чинит уже сломанные экземпляры, где писатель застрял на повёрнутом файле, не дожидаясь перезапуска.

**Что усугубляло:** уровень логирования на роутере стоит `info`, а в нём пишется каждый DNS-запрос. По умолчанию в конфиге `warn`. Если скорость роста логов будет мешать — стоит вернуть `warn`, но это решение пользователя, а не обязательная часть исправления.
